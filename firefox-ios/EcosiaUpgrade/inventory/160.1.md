# Change inventory: Firefox 159.1 to 160.1

What Firefox changed between `firefox-v159.1` (`f48a79cffc`, this branch's [`UPSTREAM_BASE`](../README.md#upstream_base)) and the upgrade target `firefox-v160.1` (`a884fb32d0`), and what each change means for Ecosia. Written for MOB-5255 on 2026-11-17, after the target moved from 159.1 to 160.1. It guides MOB-5256 (apply the 160.1 delta), MOB-5043 (lock the feature configuration) and MOB-5044 (QA test plan). The 155.1 to 159.1 part is in [159.1.md](159.1.md) and is already on `upgrade/firefox` (#1419).

- **Target:** `firefox-v160.1`, fixed by Dario on 2026-11-17. It was the latest Firefox release tag then. `firefox-origin` also has a `release/v161.0` branch (`44ff62f8e7`), but no `firefox-v161.0` tag, so 161.0 isn't released yet.
- **Sources:** the 127 commits between the two tags (`git log firefox-v159.1..firefox-v160.1`), the diff of `firefox-ios/nimbus-features/*.yaml`, `nimbus.fml.yaml`, `FeatureFlagID.swift`, `NimbusFeatureFlagLayer.swift` and `UserFeaturePreferenceManager.swift`, and a dry merge of `HEAD` (`241738c1a9`, `upgrade/firefox` after #1422) with the target, base `firefox-v159.1`.
- **Marks:** **keep** (take upstream's change), **out** (Ecosia turns it off or doesn't show it), **needs product decision** (open question for product). The decisions now in force are in the [diary](../diary/160.md#product-decisions-now-in-force), plus the three answered on 2026-11-13 (diary entry 16) and the address-bar swipe turned on on 2026-11-17.

## Architectural changes

- **Toolbar actions keep leaving Redux state** (FXIOS-17228, 17266, 17274). `numberOfTabsChanged`, `animationStateChanged`, `translucencyDidChange` and the lock icon's state move to `ToolbarModernAction` and `AddressToolbarContainerLens`. This is where Ecosia's toolbar lives again: `NavigationBarState.swift` (220 upstream lines) and `NavigationActionsBuilder.swift` conflict, and `AddressBarState`, `AddressToolbarContainer`, `AddressToolbarContainerLens` and `BrowserAddressToolbar` merge silently. Apply 159.1's trap: a refactor that moves code out of a conflicted file leaves Ecosia's change behind.
- **Search config v3** wired into routing, top sites and search telemetry (above).
- **Crash reporting:** feature-flag support in `CrashManager` and `Logger`.
- **Bottom sheets:** `OnboardingBottomSheetViewController` moves to `ComponentLibrary` as `NativeBottomSheetViewController`. Ecosia's own code doesn't use it.
- **WebEngine:** `WKEngineConfigurationProvider` becomes `DefaultWKEngineConfigurationProvider`. Ecosia's own code doesn't use it.
- **Dependencies:**
  - Sentry `exact: 9.10.0` → `9.32.0` in `BrowserKit/Package.swift`, where `Packages+Ecosia.swift` pins `exact("9.10.0")`. SPM can't resolve both.
  - Glean `from: 70.1.0` → `71.0.0`, a major version, in `MozillaRustComponents/Package.swift`, where `Packages+Ecosia.swift` has `upToNextMinor(from: "70.1.0")`.
  - application-services nightly 160.0 → 161.0.

  Bump both pins with the lockfiles, as in 159.1, and check the new versions against [SECURITY.md](../../Ecosia/Ecosia.docc/agents/SECURITY.md).
- **Glean:** new probe file `vpn.attestation.yaml`, new metrics in `metrics.yaml` and `pings.yaml`, and new live call sites in `InstallationTelemetry` and `DefaultVPNTelemetry`, both behind flags that are off. Check they compile against Ecosia's Glean setup.
- **Tests:** 24 new unit test files. `SearchViewControllerTests.swift` changed upstream, but Ecosia deleted it in MOB-4320: modify/delete conflict, keep the deletion.
