# 🛡️ Security scanning and supply chain

[Aikido](https://app.aikido.dev) scans this repository's `main` branch. This page records what we scan, what we deliberately exclude, how we judge a finding's real severity, and the supply-chain hardening already in place, so the reasoning doesn't have to be rediscovered for each new finding.

## What reaches the app, and what doesn't

The severity of a finding depends on where the affected code ends up. The project is generated by Tuist (`./tuist-setup.sh`), so the Tuist manifests, not the files that happen to be in the repository, decide what gets built.

| Source | Where it's declared | Where it ends up |
| --- | --- | --- |
| Swift packages | `firefox-ios/Tuist/ProjectDescriptionHelpers/Packages+Ecosia.swift`, resolved in `firefox-ios/Client.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` (the one CI builds with) and `firefox-ios/.package.resolved` (local builds, through the `Client.xcworkspace` symlink) | The app |
| npm packages | `package.json`, `package-lock.json` | The app: webpack bundles them into the user scripts injected into every web page |
| Nimbus and Glean generated code | `firefox-ios/nimbus.fml.yaml`, `firefox-ios/Client/Glean/` | The app, generated at setup and build time |
| Ruby gems | `Gemfile`, `Gemfile.lock` | CI only: fastlane, plus the `danger` gems that `bundler-cache` installs |
| GitHub Actions | `.github/workflows/`, `.github/actions/` | CI runners, which hold App Store and GitHub secrets |
| Python lockfiles under `firefox-ios/firefox-ios-tests/` | Mozilla's integration-test tooling | Nothing: not Tuist targets and not run by our CI, so excluded from scanning |

## Judging a finding

Aikido often lowers a finding's severity with "Downgraded: Service not internet-connected". That reasoning doesn't hold for code that ships in the app, because a browser processes untrusted web content all the time. The `dompurify` finding fixed in [#1374](https://github.com/ecosia/ios-browser/pull/1374) is the reference case: Aikido showed it as lowered, but DOMPurify sanitizes every page that Reader Mode opens.

For CI-only code, the question is whether the vulnerable code is actually executed and which secrets the job can reach. For code we don't build or run at all, we exclude the path in `.aikido` instead of patching files we don't own.

Many dependencies are inherited from Firefox. Before fixing one ourselves, check whether [mozilla-mobile/firefox-ios](https://github.com/mozilla-mobile/firefox-ios/pulls) already has a pull request for it, and cherry-pick it with `git cherry-pick -x` so the origin stays traceable.

## What `.aikido` excludes, and why

Paths in `.aikido` are relative to the repository root. The file excludes root folders that aren't part of Ecosia's product (Focus, the sample apps, taskcluster and similar), Mozilla's test tooling (`XCUITests`, `ExperimentIntegrationTests`, `SyncIntegrationTests` and `firefox-ios-tests/Tests/Pipfile`), the `evaluate_tests_to_execute` composite action that no workflow uses, and the disabled Adjust helpers.

Before adding a path, confirm three things: it isn't a source of any target in `firefox-ios/Tuist/ProjectDescriptionHelpers/Targets+*.swift`, no workflow runs it, and nothing from it is bundled into the app.

## Hardening already in place

- **Third-party GitHub Actions are pinned to commit SHAs**, written as `owner/repo@<full sha> # vX.Y.Z`. GitHub-owned `actions/*` stay on version tags. To bump one, run `git ls-remote https://github.com/<owner>/<repo>` and take the commit the new release tag points to.
- **`actions/checkout` steps set `persist-credentials: false`** unless the job pushes with the checkout token, so later steps can't read `GITHUB_TOKEN` from the git config.
- **The Nimbus FML script is pinned and checksum-verified** through `.github/scripts/download_nimbus_fml.sh`, instead of running Mozilla's `bootstrap.sh` from their `main`. See setup step 4 in the [README](README.md) for when to bump it.
- **`.github/scripts/check_pinned_dependencies.py`** fails CI when a checked-in `Package.resolved` disagrees with an `exact:` Swift package pin.

## Known gaps

These were found during the November 2026 review and haven't been addressed yet.

- Aikido has never reported a Swift package finding. It isn't confirmed whether it reads our `Package.resolved` files, so don't treat Swift packages as covered until that's verified.
- CI and local builds resolve different Swift package versions, because the two lockfiles above have drifted apart (for example SwiftSoup 2.5.3 vs 2.11.3 and Auth0 2.15.1 vs 2.17.0).
- Fuzi and GCDWebServer (both from a personal fork, `nbhasin2`) and MappaMundi track `master` instead of a version, and the `danger` gem tracks danger's git `master`.
- No GitHub workflow runs Ruby Danger, but its gems are still installed in CI.

Some Aikido findings are false positives, so they're ignored in Aikido with a reason rather than fixed (done on 3 November 2026, for the current findings only, so new findings in these files still show up). "On-screen data should be hidden when backgrounding" in `AppDelegate.swift` is already handled: `BrowserViewController` covers private tabs with a privacy window, and normal tabs are shown in the app switcher on purpose. The SSRF and file-inclusion findings in `scrape_plugins.py` and `Update_Remote_Settings.py` come from Mozilla maintenance scripts that use fixed URLs and paths.
