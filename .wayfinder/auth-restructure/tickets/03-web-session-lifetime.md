## Question
How is the web session (`EASC` cookie, Auth0 SSO cookies on the login domain) issued, how long does it live, is it refreshed by web activity, and how does the web (`/Users/paul/Development/ecosia/core/accounts`, `nxt`) decide a user is logged out? Given that, what is the cheapest reliable way for native to tell the WKWebsiteDataStore session no longer matches native auth (cookie presence/expiry in `WKWebsiteDataStore.default().httpCookieStore`, a whoami-style endpoint, web-initiated sign-in/out URL interception as today)? Also: which native-side consumers need web cookies today (`FileUploadAuthCookieSync`, AI worker presign authenticating via EASC) and is that dependency expected to go away? Read `origin/main` of core via `git show`; iOS side: `BrowserViewController+Ecosia.swift` (`handleSignInAndSignUpDetection`), `InvisibleTabSession`, `NativeToWebSSOAuth0Provider.clearSession`.

## Resolution

Sources: `core` and `platform` read at `origin/main` (fetched 2026-10-11) via `git show`; iOS at the current `main` checkout. Paths prefixed `core:` / `platform:` are repo-relative.

### Answer

1. **Issuance.** EASC is an encrypted `@fastify/secure-session` cookie (NaCl secretbox, httpOnly, secure, SameSite=Lax, path `/`, domain derived from the Auth0 issuer base URL) written by the accounts service. It is created on `/accounts/sign-in/callback` (including the session-transfer path used by iOS) and holds `{ accessToken, refreshToken, lastRefreshTime, auth0Users{userId,...} }`. It is never readable by JS. The Auth0 SSO cookie lives on `login.<domain>` and is only used for the code/session-transfer exchange; web liveness does not depend on it (web refresh tokens are offline, see below).
2. **Lifetimes (prod, today).**
   - Web access token: 1 h (`resources.tf` `token_lifetime = 3600`).
   - Web refresh token (client `ecosia_accounts`, non-rotating): 30 d idle / 90 d absolute. This was raised from 14 d / 30 d on 2026-10-06 (platform #7719). Idle resets on each exchange (Auth0 docs); the absolute limit does not.
   - EASC cookie maxAge and secure-session `expiry`: 90 d (`SESSION_COOKIE_MAX_AGE_IN_SECONDS = 7776000`). Both are reset on every successful token refresh (`session.options({maxAge})` plus `touch()`), so the cookie slides.
   - Auth0 tenant SSO session: 6 months absolute, 30 d idle (prod). Irrelevant to EASC liveness: the web refresh token is not "online" (`enforce_online_refresh_tokens = false` in prod and staging).
   - Native iOS refresh token (client `ecosia_ios_browser`, non-rotating): 14 d idle / 30 d absolute. This is **shorter** than the web token. Native credentials can therefore die while EASC is still valid (up to ~60 days of web lifetime remaining), and web can die while native lives (web idle is only consumed when a web request triggers a refresh).
3. **Refresh is request-driven, not timer-driven.** There is no background refresh. EASC's embedded access token is only renewed when a request passes through the accounts hooks (`validate-access-token` -> `refresh-access-token`, refresh when the token is within 5 min of expiry or already invalid) or nxt's `SessionCookieBasedAccountAccessorFactory` (refreshes through `POST /accounts/refresh-token` when the token is within 10 min of expiry). So EASC can legitimately hold an **expired access token** for as long as the user does not load an Ecosia web page. This is not a logged-out state.
4. **How the web decides "logged out".** All of these delete EASC and ECAU and, on the accounts side, redirect to `/accounts/sign-in?returnTo=...`:
   - No `refreshToken` in session and the access token fails verification (`validate-access-token.js`).
   - Refresh exchange fails, e.g. `invalid_grant` from idle or absolute expiry, or a revoked token (`refresh-access-token.js` -> `performSessionCleanup`).
   - nxt: decrypt, parse or expiry failure (`__ts + 90 d`), or a refresh answered 401 (`invalid-session`).
   - Explicit sign-out: `sign-out-callback.js` calls `logOut()` and `session.delete()`.

   A refresh that fails for non-401 reasons (timeout, redirect) in nxt keeps the old state and does not delete the cookie.
5. **Cheapest reliable native check.** None of the options is a true whoami, and the cookie is not self-describing:
   - **Cookie presence in `WKWebsiteDataStore.default().httpCookieStore` is a cheap but one-sided signal.** Absent or expired means the web is definitely signed out; the server deletes EASC on every cleanup path above (and the cookie store reports it via `cookiesDidChange`). Present means only "not yet found dead". The cookie value is opaque (encrypted), so native cannot read expiry or userId from it. The cookie's own `expiresDate` is the 90 d sliding window, not token validity.
   - **No whoami endpoint exists.**
     - `GET /v2/auth/chat-history` on the auth worker (`core:accounts/auth/handlers/chat-history-preference.ts`) answers 401 only when the cookie is missing, undecryptable or lacks a `userId`. It does **not** verify the access token or check refresh viability, so it cannot tell a live session from a dead one whose cookie is still in the jar.
     - `POST /accounts/refresh-token` (`core:accounts/pages/src/server/handlers/auth/refresh-token.js`, built for the extension NTP) is the closest to "validate and renew". It returns 401 if the session cannot be deserialised. Otherwise the hooks refresh a near-expiry token and respond `{ authSessionCookie }`. A failed refresh produces the session-cleanup 302. It requires sending EASC, which native can obtain from the cookie store. It is not designed for native, so adopting it is a product decision (flag for the plan, not assumed).
   - **Web-initiated interception (today's mechanism) already works as the dead-session signal.** When the server kills the session it redirects to `/accounts/sign-in`, which `BrowserViewController+Ecosia.swift` `handleSignInAndSignUpDetection` intercepts (`ios: Client/Ecosia/Extensions/BrowserViewController+Ecosia.swift:240`). Its `else` branch (native still logged in) force-logs-out natively and re-logs-in. This is the only thing today that reconciles "web dead, native alive", and it is reactive (it needs a navigation) and destructive (it clears native credentials, then re-runs the full interactive login).
   - **Recommendation for the plan.** Treat the native-credentials -> web direction as authoritative and reconcile **proactively on foreground / credentials change**, not by polling web state: (a) if native is signed in and EASC is absent from `httpCookieStore`, re-run session transfer silently (no logout); (b) keep the sign-in URL interception, but make its native-signed-in branch a silent re-transfer instead of logout+login; (c) optionally probe with `POST /accounts/refresh-token` only if a stricter "is EASC actually usable" check is needed, since cookie presence cannot prove it. Do not infer liveness from the cookie's expiry date.
6. **Native consumers of web cookies today.**
   - `FileUploadAuthCookieSync` -> `FileUploadService.uploadFile(s)`: copies EASC from WK into `HTTPCookieStorage.shared` and attaches it to the presign request (`ios: Ecosia/Core/FileUpload/FileUploadAuthCookieSync.swift`, `FilePresignRequest.swift`). `AuthSessionCookieHandler` also mirrors EASC to shared storage on every cookie change (via the `TabManagerImplementation` `WKHTTPCookieStoreObserver`, `ios: Client/TabManagement/TabManagerImplementation.swift:1318`) and `EcosiaAuthenticationService.logout` clears the copy.
   - The AI worker authenticates **only** from the cookie. `setAuthNoOptOut` calls the auth worker's `getUserSessionData(cookies)`, takes the `accessToken` *embedded in EASC*, and `requireScopes` verifies that token's signature, expiry and scopes (`core:ai-chat/ai-search-worker/common/middleware/auth.ts:75-161`). The native Bearer header is ignored (no Bearer handling anywhere in `ai-chat/ai-search-worker`; `Authorization: Bearer` is only read by `accounts/auth` `/v2/auth/token/validate`). Consequences: presign succeeds only if EASC exists **and its embedded access token is not expired**; a stale EASC token yields 403 "Forbidden" even with a fresh native token. That is the failure mode in the shared memory notes; point 3 above is its root cause, and nothing refreshes EASC for the native-only upload path (the worker has no refresh leg).
   - No native consumer of `/v2/auth/chat-history` or ECAU was found in the iOS repo.
   - Expected to go away? The Swift comment in `FilePresignRequest.swift` says Bearer support for native Auth0 clients is a "pending backend change". No such change exists on `core` `origin/main`: the AI worker still has no Bearer path. The plan must treat the EASC dependency as **current and unresolved**, to be removed only once the worker accepts native Bearer tokens (a backend dependency outside this repo). Until then, native must either ensure EASC is fresh before presign (e.g. a `POST /accounts/refresh-token` call or loading a web page first) or accept the 403 case.
7. **Related dead code.** `DataClearingIntegration.handleEcosiaAuthCookieClearing()` (logout on cookie clearing) has **no callers** in the repo (grep over `Client`, `Ecosia`, tests), so the "logout on cookie clear" behaviour described in the map is not wired today. Relevant to the "cookie-clearing integration" open item.

### Uncertainties

- **Platform docs are stale.** `core:accounts/docs/iOS-Web-Authentication-Architecture.md` (2026-03-17) says web refresh is 30 d absolute / 14 d idle with `enforce_online_refresh_tokens = true` and `enforce_cascade_revocation = true`. Current Terraform has the longer web lifetimes and both safeguards off. If the safeguards are re-enabled (the debugging change was meant to be temporary), revoking or losing the native refresh token would cascade-kill the web session and tie web liveness to native. Confirm with the Accounts team whether they will return.
- Whether Auth0 resets the **idle** timer on exchange for *non-rotating* tokens is documented only generally (the page does not state the rotation-off case explicitly). I assumed yes, which is consistent with the code comment in `refresh-access-token.js:15` ("TODO change this to 30...").
- The deployed Terraform state may differ from `origin/main` (drift, unapplied PRs); the apply status of #7719 and #7714 is not verifiable from git.
- Whether any www page or search result request refreshes EASC: nxt refreshes only on modules that use the account accessor, and accounts pages only for routes with the hooks. I did not enumerate which www pages (search vs AI search vs NTP) invoke them, so "EASC stays fresh while the user searches" is not confirmed.
- The `POST /accounts/refresh-token` behaviour for a native caller (request headers, Cloudflare Access, `userEngagement` hook side effects, the redirect-to-sign-in cleanup response) is read from code only, not exercised.
